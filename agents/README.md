# Business agent templates

Thirty fictional starting points for self-hosted receptionists. Each filename is the stable agent slug used by YAML loading and database seeding. These are examples to customize before taking real calls, not configured businesses.

## Before using a template

1. Replace the fictional name and greeting, model references, language, timezone, hours, holidays, and business policies. All examples use America/New_York and weekday hours of 09:00–18:00; weekends are closed. Recording stays off by default; decide your notice and consent policy before enabling it.
2. Supply the business knowledge listed below through the existing knowledge ingestion workflow. The YAML files intentionally omit invented FAQs, unreachable example URLs, and local files that do not exist. Without supplied knowledge, the agent offers staff follow-up rather than guessing.
3. Configure credentials for each chosen STT, LLM, and TTS provider using the existing environment settings. The example model references are defaults to replace, not bundled services. Run Postgres, Redis, LiveKit, the worker, and the voice agent as described in the root README.
4. Run `pnpm db:seed` to load the YAML examples into the default tenant. This seeds every `agents/*.yaml` file and updates matching slugs, so review the files before seeding. The runtime reads database config first, with YAML fallback; editing a file does not replace an existing database config until reseeded. Use a separate development database for experiments.
5. For native booking templates, provision an agent record in Postgres and decide whether one shared calendar is appropriate. Slot lengths below are examples. Native booking has no external-calendar, employee, room, vehicle, class, table, or stock synchronization. Request templates save leads for manual review instead of pretending to manage those resources.
6. Define who reviews saved leads and voicemails. These tools persist requests for later review; they do not notify or dispatch staff automatically or guarantee a response time. No template has a live transfer number. If needed, configure a real `transfer_call` destination and test telephony support, failure handling, emergency routing, and after-hours behavior before enabling it.

All templates support `business_hours`, `capture_lead`, and `voicemail` (runtime tool name `take_voicemail`). Native appointment templates also support availability checks, preparation, caller confirmation, and cancellation of bookings made in the same call. Handoffs use saved callbacks or voicemail by default. Sensitive-domain instructions limit the agent to reception and route clinical, legal, financial, and safety decisions to qualified people.

## Validation and evaluation

`pnpm --filter @answerline/shared test` parses every template and corresponding eval suite against the shared schemas and checks catalog coverage. `uv run pytest apps/agent/tests/test_config.py` loads every template with the Python configuration model.

Each matching `evals/<slug>.yaml` contains primary-workflow, staff-callback, voicemail, and business-limit scenarios using the current single-turn eval schema. Booking scenarios check availability rather than asserting a completed booking, because confirmation requires a later caller turn. Primary-workflow and callback scenarios assume the business is open and tools return successful results; voicemail scenarios also apply after hours. Run them with a fixed open-hours call context when the runner supports it. These scenarios are ready for the M6 runner; the current eval CLI is a stub and does not execute them. Schema validation does not prove model behavior, live call quality, or integration availability. Test real calls and emergency routing before production use.

The dashboard template picker remains tracked separately in #80; this catalog adds no dashboard UI or new tool integrations.
